# Diary

## Goal

Capture the design trail for making DMETA generated files self-describing, parseable, promotion-aware, and rich enough for LLM/tool introspection. This diary also records the decision to remove the committed generic PBUI React proof package and treat it as regenerable output.

## Step 1: Remove committed generic PBUI React proof output and create the metadata ticket

This step removed the committed `examples/street-deli-ordering/generated/pbui-react/` package after deciding that it is a proof artifact, not source of truth. The compiler and CLI can regenerate it on demand, while committed source should keep the IR, generator code, concrete profile, and promoted app surfaces.

I then created a new docmgr ticket for the metadata work. The ticket turns the follow-up requirements into a durable implementation plan: generated headers, generation command/time, source-file provenance, parseable metadata exports, promotion changelogs, and full downstream introspection of semantic and MetaDesignSystem guidance.

### What I did

- Removed `examples/street-deli-ordering/generated/pbui-react/` from the committed source tree.
- Added `.gitignore` entry for `examples/street-deli-ordering/generated/pbui-react/` so local regeneration does not dirty the tree.
- Created docmgr ticket `DMETA-GENERATED-METADATA`.
- Created the main guide:
  - `ttmp/2026/05/24/DMETA-GENERATED-METADATA--generated-file-metadata-and-promotion-guidance/design-doc/01-generated-file-metadata-and-promotion-guidance-implementation-guide.md`
- Created this diary.

### Why

- `generated/pbui-react` is reproducible proof output. Keeping it committed made generated files look like source of truth.
- The real source of truth is the Semantic IR, Interaction IR, PBUI IR, generator code, concrete PBUI profile, and promoted React apps.
- The new metadata work needs its own ticket because it spans all renderers and affects future promotion workflows.

### What worked

- The cleanup commit removed the generated proof package cleanly.
- The ticket and document workspace were created with docmgr.
- The guide now provides a concrete implementation plan and schema proposal.

### What didn't work

- Some active docs and playbooks still described `generated/pbui-react` as retained proof output. I updated them after creating the guide so they now describe it as ignored/regenerable output.

### What I learned

- The generated metadata work should be implemented as a shared renderer/metadata package rather than by copying header logic into each target renderer.
- The current renderers already have partial metadata concepts; the next step is unification and richer source references.

### What was tricky to build

- The metadata requirements cross several layers: core registry generation, Web React scaffolding, generic PBUI React scaffolding, and concrete PBUI/CLIM app scaffolding. The guide needed to keep those target differences clear while proposing one shared metadata schema.
- The phrase "input files were relevant and why" implies more than file lists. Plans need source references with roles and reasons, not just paths.

### What warrants a second pair of eyes

- Review the proposed `GeneratedFileMetadata` schema before implementation.
- Review which file kinds should be marked promotable by default.
- Review whether generation time should be wall-clock time or deterministic build metadata in tests.

### What should be done in the future

- Implement `pkg/dmeta/generator/metadata` with shared structs and render helpers.
- Thread generation context from CLI commands into renderers.
- Add parseable metadata exports to generated TS/TSX files.
- Add promotion changelog blocks to promotable file kinds.
- Add tests for Web, PBUI, and concrete PBUI/CLIM renderers.

## Step 2: Validate the metadata guide and restore missing shared examples

This step validated the new ticket material and checked that the generic PBUI proof package can still be planned after being removed from the committed tree. During validation, `go test ./pkg/dmeta/... ./cmd/dmeta -count=1` exposed that the shared core-model example files were missing from the working tree because of a previous cleanup commit. Those examples are referenced by `sources/dmeta-ir/01-core-model.yaml`, so the core generator tests correctly failed.

I restored the missing shared examples from the last commit that contained them and reran the tests. After restoration, Go tests and the PBUI React plan command passed. This keeps the source package coherent while still leaving `generated/pbui-react` ignored and regenerable.
