# Generated File Metadata and Promotion Guidance Implementation Guide

## 1. Purpose

This guide explains how to make every generated DMETA file self-describing. A new intern should be able to open a generated React file and answer four questions without reading the entire compiler first:

1. Which command generated this file?
2. When was it generated?
3. Which source files were relevant, and why?
4. What semantic, interaction, MetaDesignSystem, and target metadata should guide future edits?

The same file should also be useful to tools. Human-readable comments are not enough. Wherever possible, generated TypeScript files should export a parseable metadata object. JSON metadata sidecars should use the same schema. Future lint checks, editor tooling, Storybook addons, and LLM-assisted development workflows should be able to read the metadata and reason about provenance.

There is a second requirement. Some generated files are meant to be promoted into maintained code. Those files need a short promotion guide and a changelog section at the top. Once a generated scaffold becomes maintained app code, every meaningful human change should be recorded near the file's metadata. That gives future developers and LLM agents context about why the file diverged from generated output.

This ticket is about the metadata and promotion layer. It is not about changing the semantics of Web or PBUI lowering. It is about preserving the information that already exists in the compiler and making that information visible in the files developers actually edit.

## 2. The current problem

DMETA already carries rich information through its compiler pipeline. The source YAML files contain prose fields. The Go plans know which passes produced which artifacts. The renderers emit some headers and metadata sidecars. The generated core registries contain full archetype and capability descriptions. The PBUI concrete presentation plan contains presenter intent, recognizer intent, concrete renderer bindings, surfaces, views, style classes, and source pass names.

The problem is that the final files a developer opens do not consistently expose this information.

A component file may say only:

```ts
// Code generated by dmeta scaffold-react from Web MetaDesignSystem obligations. DO NOT EDIT until promoted.
```

That is useful, but incomplete. It does not say when the file was generated, which exact command was used, which source files mattered, which representations and actions were realized, what prose from the archetypes and capabilities should guide the implementation, or whether the file is intended to be promoted.

The system also lacks a consistent promotion convention. A scaffolded file may become maintained code, but the file itself does not always tell the next agent how to record changes, which generated sections should remain stable, or which metadata should not be deleted.

## 3. Desired end state

Every generated file should begin with a generated-file prelude. The prelude has three layers:

1. A short human header.
2. A parseable metadata export or sidecar entry.
3. A promotion guidance block when the file is promotable.

For TypeScript and TSX files, the ideal shape is:

```ts
// Code generated by dmeta scaffold-react. DO NOT EDIT until promoted.
// Generated at: 2026-05-25T14:03:22Z
// Command: dmeta scaffold-react --instance ./examples/... --target react --force
// Metadata: dmetaGeneratedMetadata below is the source of truth for tooling.

export const dmetaGeneratedMetadata = {
  schemaVersion: 1,
  generated: {
    at: '2026-05-25T14:03:22Z',
    by: 'dmeta scaffold-react',
    command: 'dmeta scaffold-react --instance ./examples/... --target react --force',
    gitCommit: 'optional-if-known'
  },
  artifact: {
    path: 'src/widgets/AppointmentBlock/AppointmentBlock.tsx',
    kind: 'component',
    language: 'tsx',
    promotable: true
  },
  pipeline: {
    semanticRoot: './examples/appointment-admin',
    interactionsRoot: './sources/dmeta-ir',
    metaDesignSystem: 'web',
    target: 'react',
    passes: ['validate-ir', 'elaborate-interactions', 'lower-web', 'plan-scaffold', 'scaffold-react']
  },
  sources: [
    {
      path: './examples/appointment-admin/core-model/appointment-admin.yaml',
      role: 'domain semantic mappings',
      why: 'Defines Appointment, Client, Practitioner, TimeSlot, Room, and Service domain mappings.'
    },
    {
      path: './sources/dmeta-ir/interactions/actions.yaml',
      role: 'interaction actions',
      why: 'Defines reschedule, cancel, inspect, assign, and filter actions realized by this component.'
    }
  ],
  semantics: {
    domainTypes: ['Appointment'],
    archetypes: ['WorkItem', 'TimelineSpan'],
    capabilities: ['identifiable', 'labelable', 'stateful', 'temporal', 'schedulable'],
    representations: ['appointment_calendar_block', 'appointment_summary'],
    actions: ['inspect_subject', 'reschedule_appointment', 'cancel_appointment']
  },
  guidance: {
    summary: 'Render an appointment as a schedulable stateful work item.',
    implementationNotes: [
      'Preserve appointment identity in data attributes.',
      'Do not hide cancellation or conflict state behind color alone.',
      'Keep action callbacks typed and external to this component.'
    ]
  }
} as const;

/**
 * Promotion changelog
 * - 2026-05-25: Generated by dmeta scaffold-react. Not promoted yet.
 *
 * Promotion instructions
 * - Keep dmetaGeneratedMetadata unless the file is deliberately detached from DMETA.
 * - Record every semantic or behavioral change in this changelog.
 * - Update Storybook when visual states or interaction behavior change.
 */
```

The exact fields can evolve, but the idea should not change. Generated files should explain themselves in a way that is readable by humans and parsable by tools.

## 4. Why parseable metadata matters

DMETA is designed for LLM-assisted and tool-assisted development. That means a future assistant may open a component file before reading the source YAML. The component should confront the assistant with the actual system metadata rather than leaving it to infer intent from JSX alone.

Parseable metadata enables several future capabilities:

- A lint rule can detect when a promoted component deleted required provenance.
- A Storybook addon can display source archetypes, capabilities, actions, and lowering rules.
- An editor command can jump from a component to its source YAML files.
- A regression script can compare generated metadata with current source IR and detect stale promoted files.
- An LLM can read a component and see the semantic obligations it must preserve.

Comments alone help humans. Parseable metadata helps humans and programs.

## 5. Metadata schema proposal

Use a shared schema across all generated targets. The schema should be represented in Go and emitted as JSON-compatible data.

Pseudocode Go model:

```go
type GeneratedFileMetadata struct {
    SchemaVersion int `json:"schemaVersion"`
    Generated GeneratedInfo `json:"generated"`
    Artifact ArtifactInfo `json:"artifact"`
    Pipeline PipelineInfo `json:"pipeline"`
    Sources []SourceReference `json:"sources"`
    Semantics SemanticGuidance `json:"semantics,omitempty"`
    Web *WebGuidance `json:"web,omitempty"`
    PBUI *PBUIGuidance `json:"pbui,omitempty"`
    React *ReactGuidance `json:"react,omitempty"`
    Guidance HumanGuidance `json:"guidance,omitempty"`
    Promotion *PromotionInfo `json:"promotion,omitempty"`
}

type GeneratedInfo struct {
    At string `json:"at"`
    By string `json:"by"`
    Command string `json:"command"`
    WorkingDirectory string `json:"workingDirectory,omitempty"`
    GitCommit string `json:"gitCommit,omitempty"`
}

type SourceReference struct {
    Path string `json:"path"`
    Role string `json:"role"`
    Why string `json:"why"`
    ArtifactType string `json:"artifactType,omitempty"`
}
```

The schema should be target-neutral. Web-specific fields belong under `web`. PBUI-specific fields belong under `pbui`. React-specific fields belong under `react`. Shared semantic facts belong under `semantics`.

## 6. Source references

Every generated file should include relevant input files with reasons. Do not list the entire repository. List files that materially shaped the artifact.

For a Web React component, relevant inputs usually include:

- the application semantic package;
- shared Interaction IR action/representation files;
- Web MetaDesignSystem package files;
- local Web lowering rules;
- the instance manifest;
- React target configuration.

For a generic PBUI React file, relevant inputs usually include:

- the application semantic package;
- shared Interaction IR files;
- global PBUI `presentation-types.yaml`;
- global PBUI `lowering-rules.yaml`;
- global PBUI `targets/react.yaml`.

For a concrete PBUI/CLIM React app file, relevant inputs usually include:

- all generic PBUI inputs above;
- `presentation-system.yaml`;
- `style-profile.yaml`;
- `surfaces.yaml`;
- `view-models.yaml`;
- `presentation-bindings.yaml`;
- `targets/react-app.yaml`;
- static prototype files such as `www/clim/index.html`, `www/clim/styles.css`, and `www/clim/js/app-main.js` when they influence the generated file.

Each source reference must include `why`. A path without a reason is not useful enough.

## 7. Introspection content from Semantic IR

The final React files should preserve enough semantic guidance to help a developer implement the file correctly.

For a component derived from an object type, include:

- domain type ids;
- archetype ids;
- capability ids;
- inherited effective capabilities where relevant;
- required projections;
- related semantic presentations;
- related semantic actions;
- short and long descriptions from archetypes/capabilities when the file is a primary realization of those concepts.

Do not dump every global archetype into every file. The goal is relevant context. A component that renders `AppointmentBlock` needs appointment-related archetypes and capabilities. It does not need every unrelated global concept.

The core renderer already proves this is possible. `pkg/dmeta/generator/core/render.go` emits TypeScript registries containing archetype descriptions, long descriptions, inheritance, capabilities, presentations, and actions. The target renderers should reuse that information or derive a relevant subset for each generated artifact.

## 8. Introspection content from Interaction IR

Files that realize interactions should include:

- representation ids;
- action ids;
- accepted subject types;
- required argument types;
- confirmation/danger semantics;
- source elaboration rule ids;
- presenter or recognizer intent when available.

For PBUI files, this is especially important. A `PresentationRefLine` is not just a visual line. It is a typed object that can be selected, inspected, copied, and used as an action argument. The generated metadata should make those obligations explicit.

## 9. Introspection content from MetaDesignSystems

Web files should include Web metadata:

- widget template id;
- slots;
- visual states;
- event bindings;
- lowering rule ids;
- target file kinds;
- intended Storybook coverage.

PBUI files should include PBUI metadata:

- PBUI presentation type id;
- presenter intent;
- recognizer intent;
- action presentation semantics;
- object/action descriptor references;
- concrete renderer binding if a profile is applied.

Concrete PBUI/CLIM files should also include profile metadata:

- profile id;
- view id;
- surface id;
- component binding;
- style classes;
- source static prototype references;
- runtime architecture notes from the profile.

This is the metadata that should confront future LLM agents. If an agent edits `ActionPresentationInline.tsx`, it should see that this component implements `pbui.action_presentation`, where it appears, which actions it represents, and how it participates in selection or command flow.

## 10. Promotion changelog and instructions

Some generated files are meant to be promoted. These files need extra content at the top.

A promoted file prelude should include:

```ts
/**
 * DMETA promotion status: scaffold
 *
 * Promotion instructions:
 * - Keep dmetaGeneratedMetadata in this file.
 * - When changing behavior, update the Promotion changelog below.
 * - When changing props or visual states, update the matching Storybook stories.
 * - When changing semantic behavior, update source IR or explain why this file intentionally diverges.
 *
 * Promotion changelog:
 * - 2026-05-25: Generated by dmeta scaffold-react. Initial scaffold.
 */
```

When a human promotes the file, they should change status from `scaffold` to `promoted` and add a new changelog entry:

```ts
/**
 * DMETA promotion status: promoted
 *
 * Promotion changelog:
 * - 2026-05-25: Generated by dmeta scaffold-react. Initial scaffold.
 * - 2026-05-26: Promoted to production component. Replaced placeholder slots with typed AppointmentViewModel props and added keyboard selection behavior.
 */
```

The file-level changelog is intentionally short. It is not a replacement for Git. It is a local semantic history for future maintainers and LLM agents.

## 11. Which files are promotable

Not every generated file needs promotion guidance.

Usually promotable:

- React components;
- React hooks if humans are expected to refine them;
- Storybook stories;
- adapter TODO files if they become maintained adapters;
- view components;
- presentation renderer components;
- command/context menu components.

Usually not promotable:

- `package.json`;
- `tsconfig.json`;
- generated registry files that should be regenerated exactly;
- generated metadata JSON sidecars;
- generated index barrels unless humans intentionally maintain them.

The metadata schema should include:

```json
"promotion": {
  "promotable": true,
  "status": "scaffold",
  "instructions": [...],
  "changelog": [...]
}
```

For non-promotable generated files, set `promotable: false` and explain whether the file should be regenerated instead of edited.

## 12. Implementation plan

### Phase 1: Introduce shared metadata model

Add a package for generated metadata, for example:

```text
pkg/dmeta/generator/metadata/model.go
pkg/dmeta/generator/metadata/render.go
```

This package should define:

- `GeneratedFileMetadata`;
- source reference structs;
- promotion structs;
- helpers to render comment headers;
- helpers to render TypeScript `dmetaGeneratedMetadata` exports;
- helpers to render JSON sidecars.

The helpers should avoid target-specific knowledge. Targets provide metadata content; the shared package formats it consistently.

### Phase 2: Capture generation command and time

The CLI commands should pass generation context into renderers:

```go
type GenerationContext struct {
    GeneratedAt time.Time
    CommandName string
    CommandLine []string
    WorkingDirectory string
    GitCommit string
}
```

The command line can come from `os.Args`. The working directory can come from `os.Getwd()`. The git commit is optional; if it is expensive or unavailable, leave it empty.

The important rule is that the metadata should say when and how the file was generated.

### Phase 3: Add source references to plans

The React plan structs already contain some provenance. Extend them so every planned file can carry relevant source references.

Web path candidates:

```text
pkg/dmeta/generator/react/model.go
pkg/dmeta/generator/react/plan.go
```

PBUI generic path candidates:

```text
pkg/dmeta/metadesign/pbui/react_plan.go
pkg/dmeta/metadesign/pbui/react_render.go
```

Concrete PBUI app candidates:

```text
pkg/dmeta/metadesign/pbui/profile/react_app_plan.go
pkg/dmeta/metadesign/pbui/profile/react_app_render.go
```

Plans should not merely say `sourceRules`. They should include input file paths and reasons.

### Phase 4: Render parseable metadata in TypeScript

For TypeScript and TSX files, render an exported metadata object when possible:

```ts
export const dmetaGeneratedMetadata = { ... } as const;
```

For files where an export is not appropriate, use a sidecar JSON file or a block comment with embedded JSON. Prefer exports for TS/TSX because they are easy for tooling to import.

Avoid naming collisions. If a file already exports a `dmetaGeneratedMetadata`, regeneration should preserve or overwrite it only in scaffold-stage files. For promoted files, future tooling should detect and report drift rather than silently overwriting.

### Phase 5: Render promotion guidance

Add promotion prelude blocks to promotable file kinds.

Web file kinds likely promotable:

```text
component
types
stories
adapter_todo
style
readme
```

PBUI concrete app file kinds likely promotable:

```text
shell_component
command_line_component
command_bar_component
context_menu_component
confirm_prompt_component
presentation_component
action_presentation_component
view_component
shell_story
command_line_story
command_bar_story
context_menu_story
confirm_prompt_story
presentation_story
action_presentation_story
view_story
```

Generic registries are usually not promotable. They should be regenerated.

### Phase 6: Expose rich IR guidance downstream

Add relevant semantic and MetaDesignSystem content to generated metadata.

For Web components, include:

- template id;
- representations/actions realized;
- domain types;
- archetype/capability ids and descriptions when available;
- slots, states, event bindings;
- source lowering rule id and rationale.

For PBUI components, include:

- PBUI presentation type id;
- presenter intent;
- recognizer intent;
- object/action descriptors;
- concrete binding component;
- view/surface placement;
- style profile class names;
- source YAML references.

### Phase 7: Add tests

Add tests that assert:

- generated TS/TSX files include the generated header;
- generated TS/TSX files export `dmetaGeneratedMetadata` where applicable;
- metadata includes command, time, source paths, and reasons;
- promotable file kinds include promotion instructions and changelog;
- non-promotable registries mark themselves as regenerable;
- metadata sidecars and inline exports agree on core fields.

Candidate test files:

```text
pkg/dmeta/generator/metadata/render_test.go
pkg/dmeta/generator/react/render_test.go
pkg/dmeta/metadesign/pbui/react_render_test.go
pkg/dmeta/metadesign/pbui/profile/react_app_render_test.go
```

## 13. Regenerable PBUI proof package policy

The generic PBUI React proof package used to be committed under:

```text
examples/street-deli-ordering/generated/pbui-react/
```

It is now treated as regenerable output. The directory should be ignored by Git and generated on demand with:

```bash
go run ./cmd/dmeta scaffold-pbui-react \
  --root ./examples/street-deli-ordering \
  --interactions-root ./sources/dmeta-ir \
  --pbui-root ./sources/dmeta-ir/meta-design-systems/pbui \
  --output-dir ./examples/street-deli-ordering/generated/pbui-react \
  --dry-run=false \
  --force \
  --output table
```

This policy is consistent with the metadata work. Generated proof output should be easy to recreate and inspect. Promoted apps such as `www/mobile-react` and `www/clim-react` remain committed because they are maintained application surfaces.

## 14. Acceptance criteria

The ticket is complete when:

- every generated file has a consistent generated header;
- every generated file records generation time, command, and source inputs with reasons;
- TS/TSX generated files export parseable metadata when possible;
- metadata sidecars use the same schema as inline metadata;
- promotable generated files include promotion instructions and a file-level changelog;
- generated Web React files expose relevant Semantic IR, Interaction IR, and Web MetaDesignSystem guidance;
- generated PBUI files expose relevant Semantic IR, Interaction IR, PBUI, and concrete profile guidance;
- tests enforce the presence and shape of metadata;
- docs explain how to regenerate ignored proof outputs such as `generated/pbui-react`.

The implementation should be incremental. First create the shared metadata schema. Then update one target renderer and its tests. Then update the others. Do not attempt to redesign Web lowering or PBUI lowering while implementing metadata. The goal is to surface existing information, not to change the compiler's meaning.
